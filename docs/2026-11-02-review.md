# pi-async 评审：流程、能力与 pi 1.5.0 适配建议

- 日期：2026-11-02
- 评审对象：`/root/code/pi-async` @ `fba7b46`（HEAD）；npm 实际安装版本 `0.2.0`
- 宿主：pi `1.5.0`（本机同时保留 `1.2.0` / `1.4.0` 供对照）
- 方法：7 路只读侦察（核心引擎、TUI、pi API diff、质量门、1.5 文档、真实使用数据、契约），关键结论二次核验
- 质量门基线：`npm run typecheck` 通过；`npm test` **182/182 通过**

---

## 0. 结论摘要

**架构是合理的，能力也是真差异化；问题不在“想法”，而在“实现承诺与运行时现实之间的缝”。**

三句话：

1. **它填补了 pi 的真实空白。** pi 1.5.0 仍没有官方后台任务、队列、watch、任务面板；pi-async 的 5 工具 + 进程组 kill + 输出落盘 + watch + 唤醒，是 pi 生态里独特的一层。不要把它改成 agent 编排器，那是 legion 的活。
2. **当前最大的风险是“状态面说谎”。** `ui.setActivity`、`ui.copyToClipboard` 在官方 pi 1.2/1.4/1.5 都不存在；`sendMessage` 返回 `void`，通知重试/回滚是死代码；settle-guard 写的提醒进不了 LLM context；`spawn` 不传 session cwd；`/reload` 会 kill 正在跑的任务。用户看到的“能力”和实际生效的行为有差距。
3. **先发版，再谈增强。** HEAD 已有 6 个未发版提交，其中包含 2026-10-21 的 stale-ctx 崩溃修复；npm 上的 0.2.0 仍带这个会杀死 pi 进程的缺陷。不发布，后面所有修复都等于零。

**产品定位建议：**

> pi 的后台 shell 任务运行时：执行、观测、取回，状态面永不说谎。
> TUI 是可选观测面；agent 编排、OSC busy 上报、跨扩展事件总线都不该是它的主线。

## 1. 它现在是什么

### 1.1 对外能力面

| 面 | 内容 | 评价 |
|---|---|---|
| 工具 | `async_run` / `async_wait` / `async_status` / `async_logs` / `async_kill` | 5 工具面干净，冻结契约明确 |
| 运行模式 | `background` / `delayed` / `sync` | 覆盖“长任务、定时、前台带超时”三类真实需求 |
| 超时 | `sync.timeoutMs` + `taskTimeoutMs` + `onTimeout=promote/abort` | promote/abort 都转后台、都不杀进程；语义需更清楚 |
| watch | 5 种条件：`exit_code` / `stdout_contains` / `stderr_contains` / `json_path_exists` / `output_matches` | 差异化能力；但组内是 OR、盲检只计 error、64K 字符窗口，需写清 |
| 进程管理 | `/bin/sh -c` + `detached` + 进程组 SIGTERM→SIGKILL + `/proc` 确认 | 这是最硬的一块，保留 |
| 输出 | 合并 `.output` + 分流 `.stdout` / `.stderr`，默认 20 MiB cap，0600 | 设计好；读路径目前整文件读 |
| 持久化 | 每任务 `.json` + 输出文件，原子 rename，reload 恢复 pending/running | 方向对；reload 语义不完整 |
| 通知 | `sendMessage({customType, content: XML}, {deliverAs:"followUp", triggerTurn:true})` | 通道对；可靠性实现不成立 |
| TUI | rail（≤4 行）+ `/async` 面板（80%×70%）+ `/async-clear` | 视觉与 cell 宽度处理不错；交互与刷新有硬伤 |
| settle guard | legion child 在 `agent_before_settle` 提醒未收尸任务 | 目标对；实现进不了模型上下文 |
| 契约/测试 | `docs/CONTRACT.md` 冻结 + 182 测试 | 工程纪律高于同类扩展 |

### 1.2 一个任务的完整生命周期

```text
工具调用 async_run
  → tools/index.ts 参数校验（模式互斥、必填、watch 禁止 sync）
  → registry.submit / scheduleDelayed / runSync
      → assertAdmission（running+pending < 32，无队列，直接 throw）
      → spawnDetached(/bin/sh -c, detached, stdout/stderr→pipe)
          → 三路写盘：.output / .stdout / .stderr（0600）
          → 逐 chunk 计数，超 20MiB → persistOutputCap + killTree
      → task.status=running（delayed 先 pending + dueAt）
      → watch loop（≥1s 轮询，failure_when 优先，success_when 命中→completed）
      → child close → finalize(status, killKind/failureKind)
          → persist（原子写）
          → events.onFinalize
              → logs(8KiB tail) → sendCompletionNotification(followUp + triggerTurn)
          → events.onStateChange（activity + TUI 刷新）
          → prune（仅终态，100 个 / 7 天）
  → async_wait 等待：finalize 唤醒 waiter；wait 结果会 consume → 抑制通知
```

关键文件：`extensions/index.ts`、`src/tools/index.ts`、`src/core/registry.ts`、`src/core/spawn.ts`、`src/core/watch.ts`、`src/core/notify.ts`、`src/guard/settle-guard.ts`。

### 1.3 值得保留的设计

- **进程组 kill + 确认**：SIGTERM → 3s → SIGKILL → 1.5s 探测；`/proc` 不可用时降级 `kill(-pid, 0)`；失败不静默，抛“Descendant processes may have leaked”。
- **输出安全**：ANSI/OSC/C0 剥离、UTF-8 边界截断、XML 转义、20 MiB cap。
- **watch 三态**：matched / pending / error，failure 优先，pending 不消耗盲检（设计意图正确，虽然实现有边界问题）。
- **持久化 + reload**：原子 rename、pending delayed 恢复、running 收养、lost 标记。
- **TUI cell 宽度**：CJK/emoji 截断、ANSI 感知、帧宽一致性测试。
- **契约与测试**：5 工具面冻结、REV 记录、182 个测试、CI 双 workflow。

## 2. 与 pi 1.5.0 的对齐

### 2.1 版本事实

| 事实 | 证据 |
|---|---|
| 最新安装版是 pi **1.5.0** | `/root/.pi/agent/install/releases/1.5.0/...` |
| pi-async 的 `peerDependencies` 是 `^1.2.0` | `package.json:60-63` |
| 仓库内 `node_modules` 实际装的是 **1.2.0** | 因此 `tsc --noEmit` 的类型基线不是 1.5.0 |
| 1.4.0 → 1.5.0 的扩展事件钩子**零变更** | 两版 `types.d.ts` 的 `on(...)` 重载完全一致 |
| 1.5.0 唯一破坏性变更：工具参数校验改走 `@earendil-works/pi-schema` | pi 1.5.0 `CHANGELOG.md:14` |
| 1.5.0 新增：`keyHint/keyText`、`ctx.ui.custom({blocked})`、`pi.exec maxBuffer/truncated` | `types.d.ts:73-79,146-149`、`exec.d.ts:14-31` |
| 1.5.0 仍无官方 async/background/队列/任务面板 | docs/CHANGELOG/examples 均无 |

**结论：没有“不升级就坏”的 API 破坏。** 风险在行为层：pi-schema 会让工具参数错误文案和宽松转换变化，`^1.2.0` 无法表达这种差异。

### 2.2 pi-async 用到的 API 逐项状态

| API | 用途 | 1.5.0 状态 | 判定 |
|---|---|---|---|
| `registerTool` | 5 工具 | 在；execute 有第 5 参 `ctx: ExtensionToolContext` | 可用；未接 `ctx.cwd` / `onUpdate` |
| `registerCommand` | `/async`、`/async-clear` | 在 | 可用；仅在 TUI ctx 绑定后注册 |
| `pi.on("session_start"/"message_start"/"session_shutdown")` | 生命周期 | 在；`session_shutdown` 有 `reason` | 未读 `reason` |
| `pi.on("agent_before_settle")` | settle guard | 在；**aborted run 会跳过** | 语义不匹配 |
| `pi.appendEntry` | 提醒/心跳 | 在；`custom` entry **不进 LLM context** | 提醒无效 |
| `pi.sendMessage` | 完成通知 | 在；**返回 `void`**，宿主 fire-and-forget | 重试/回滚死代码 |
| `ctx.ui.setWidget` | rail | 在 | 可用 |
| `ctx.ui.custom({overlay})` | panel | 在；overlay 忽略 `blocked` | 可用 |
| `ctx.ui.setStatus` | footer 汇总 | 在 | **未使用**（HEAD 已下架 footer） |
| `ctx.ui.setActivity` | activity/OSC | **1.2/1.4/1.5 均不存在** | 三处调用全是 no-op |
| `ctx.ui.copyToClipboard` | 面板复制路径 | **不存在** | 永远走 notify fallback |
| `pi.exec` | 执行命令 | 在；1.5 新增 maxBuffer/truncated | 未用；自建 spawn 合理 |
| `ctx.cwd` / `ctx.sessionManager` | session 上下文 | 在（`ExtensionContext`） | **未用**，导致 cwd 错误 |
| `promptSnippet` / `promptGuidelines` | 工具发现 | 在 | 未用 |
| `onUpdate` | 工具进度 | 在 | 未用 |
| `registerMessageRenderer` | 通知卡片 | 在 | 未用（裸 XML） |
| `keyHint` / `keyText` | 快捷键提示 | 1.5 新增 | 未用 |

### 2.3 1.5.0 提供、但 pi-async 还没吃到的东西

- **`ctx.cwd`**：修 cwd 的正确来源，直接接进 `execute` 第 5 参即可。
- **`onUpdate`**：sync/async_wait 长调用可以流式报“已等多久 / 最后一行输出”，避免工具行只有 spinner。
- **`promptSnippet` / `promptGuidelines`**：让模型在系统提示的 `<tools>`/`<rules>` 里看到何时该用 async_run，而不是把整段说明塞进 `description`。
- **`pi.exec maxBuffer/truncated`**：短命令可复用；长任务仍应自建 spawn（需要 detached、env、进程组 kill，pi.exec 不支持）。
- **`registerMessageRenderer`**：把裸 XML 通知渲染成卡片，显著降低“通知像日志”的观感。
- **`keyHint`**：面板/rail 的快捷键提示不再硬编码，跟随宿主键位。
- **`ctx.ui.setStatus`**：在 `setActivity` 不可用的现实下，footer 状态是唯一官方“常驻状态”通道；可替代当前空转的 activity。
- **`pi-schema`**：1.5.0 校验器变化需要在 CI 里用 1.5.0 实测，而不是继续用 1.2.0 类型基线。

## 3. 问题清单

### P0：会破坏信任 / 丢工作 / 泄漏

#### P0-1 发布断层：用户在跑带崩溃缺陷的 0.2.0

- **事实**：HEAD `fba7b46` 是 2026-10-22 的 stale-ctx 崩溃修复；npm 安装包 `/root/.pi/agent/npm/node_modules/pi-async` 仍是 0.2.0（2026-10-16），其 `extensions/index.ts` 没有 `activeGuard.dispose()`。
- **影响**：settle-guard 心跳在旧 ctx 上抛错 → `uncaughtException` → pi 退出。修复已在 HEAD，但没发版。
- **建议**：0.3.0 一次性发布（见 §4.1）；如果发布流程超过一周，先切 0.2.1 只带崩溃修复。

#### P0-2 任务不继承 session cwd

- **事实**：`spawnDetached` 的 `spawn()` 没有 `cwd` 选项（`src/core/spawn.ts:25`），任务继承 pi 进程的 `process.cwd()`；工具 `execute` 只接 3 参，没有用 `ctx.cwd`（`src/tools/index.ts:60`）。pi 1.5 的 `ExtensionToolContext` 明确提供 `cwd`（`types.d.ts:288` → `ExtensionContext.cwd:240`）。
- **影响**：用户在 pi 里 `cd` 到子目录/另一个仓库后跑 `async_run("pwd")`，命令在启动 pi 的目录执行。对“在项目里跑构建/测试”的核心场景是致命错误。
- **建议**：`execute(_id, params, signal, _onUpdate, ctx)` → `registry.submit(..., { cwd: ctx.cwd })`；`spawnDetached` 传 `cwd`；delayed 任务持久化 `cwd`，reload 恢复；TUI `R` 重跑用最近一次 session cwd。

#### P0-3 通知链路：重试/回滚是死代码，claim 在投递前

- **事实**：
  - `ExtensionAPI.sendMessage` 返回 `void`（pi 1.5 `types.d.ts:1281-1285`）；宿主内部 `.catch` 成 extension error，调用方拿不到失败。
  - `notify.ts:44-55` 的 `await target.sendMessage(...)` + `catch` + 3 次重试，在真实宿主上永远不会进入失败分支。
  - `claimNotification` 在发送前把 `notified=true` 落盘（`registry.ts:353-356`）；一旦发送失败/进程崩溃，下一代 reload 不会补发。
  - `async_wait` 取到结果会置 `outputConsumed=true`（`registry.ts:502-505`），从而抑制通知；这是设计，但文档没写清。
- **影响**：用户以为“完成会叫醒我”，实际可能永久静默；实测 legion 仓库 28 条完成任务中 21 条 `notified=false`（多数是被 wait 消费，但说明通知不是主路径）。
- **建议**（无 ack API 下最诚实的做法）：
  1. 删掉 3 次重试与 rollback；只调用一次，把 `sendMessage` 返回视为“已交给宿主”，不等于“模型看到”。
  2. `claim` 后置：先 `notifyAttempts++`，调用成功再置 `notified=true`；失败保持 false。
  3. `session_start` 对“终态 + `notified=false` + `!outputConsumed` + 24h 内 + attempts<2”的任务补发一次。
  4. `async_status` 明确暴露 `notified` / `outputConsumed`，让模型能自查“我是不是漏了通知”。
  5. 可选：用 `ctx.sessionManager.getEntries()` 查 `custom_message` 是否已在会话里，作为“已送达”的弱确认；成功才置 `notified=true`，失败保持 false。

#### P0-4 settle-guard 的提醒模型看不到，Esc 时完全不触发

- **事实**：
  - `settle-guard.ts:52-58` 用 `appendEntry("async-task-settle-reminder", ...)`；pi 文档明确 `custom` entry **不参与 LLM context**，只有 `custom_message` 才会贡献 user-role 消息。
  - 返回 `{continue: true}` 只保证一次 context-only 请求，并不保证提醒进入上下文。
  - `agent_before_settle` 只在 `PI_LEGION_NODE_ID` 存在时注册；主会话没有守卫。
  - pi 1.5 文档明确 **aborted run 跳过 `agent_before_settle`**（`docs/extensions.md:336`），Esc 中断场景零覆盖。
  - 60s 心跳写 `async-task-heartbeat` entry；legion 的 `collectArtifactGrowing` 只观察 **500ms 窗口**内的 session 文件增长（`pi-legion/orchestrator.ts:2931-2939`），60s 心跳几乎不可能命中，**不能作为“续期”依据**。
- **影响**：README/CONTRACT 宣称的“legion child 不会带着未收尸任务报 verdict”并未真正成立。
- **建议**：
  1. `agent_before_settle` 返回 `entries: [...event.entries, {type:"custom_message", customType, content, display:false}], continue:true`。
  2. 增加 `agent_settled` + `event.aborted` 兜底：若被中断且有活跃任务，发一条 `sendMessage({deliverAs:"followUp"})` 待读提醒（不依赖 `triggerTurn`）。
  3. 心跳要么删掉，要么改成对 legion 真正可消费的显式 liveness 信号（文件 mtime/事件），不要继续写无人读的 entry。
  4. 是否对所有会话启用：不建议无条件 `continue:true`（文档明确可造成死循环）；先 legion-only，主会话用 `async_status` 提示。

#### P0-5 `/reload` 会 kill 正在跑的任务，reload 恢复不完整

- **事实**：`extensions/index.ts:145-153` 的 `session_shutdown` 忽略 `event.reason`，直接 `registry.shutdown()`；`shutdown()` 对所有非 pending 且进程仍活的任务 `kill(id, "shutdown")`（`registry.ts:375-390`）。
- **影响**：用户 `/reload` 扩展，后台构建/测试被 SIGTERM；reload 后 `taskTimeoutMs` 不重建、watch 超时预算重置、退出码丢失、waiter 不持久化。
- **建议**：
  - `reason === "reload"`：不 kill，持久化并让下一代收养（pid 活则继续，dead 则 lost）。
  - `reason === "quit"` / `SIGTERM`：kill。
  - `new` / `fork` / `resume`：按产品语义决定（建议 kill 或明确归属，避免跨会话泄漏）。
  - 持久化 `timeoutAt`、`watchDeadline`、`cwd`，reload 时重建；退出码不可恢复的标 `lost` 并说明。

#### P0-6 环境变量与输出路径的安全面

- **事实**：
  - `spawnDetached` 用 `{...process.env, ...opts.env}`（`spawn.ts:23`），子进程拿到全部 provider 凭证（`ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 等）。
  - `env` 来自 LLM 参数（`tools/index.ts:58`），模型可覆盖 `PATH` / `LD_PRELOAD` / `NODE_OPTIONS`。
  - delayed 任务的 `metadata.delayedEnv` 明文进 `.json`（`registry.ts:64`），并在 `async_status` / 面板 metadata 中原样展示。
  - `async_logs` 信任 `metadata.outputFile`（`registry.ts:303-308`），本地改 `.json` 可让它读任意文件。
  - 输出落在项目目录 `.pi/async/`，可能被 git/分享带走。
- **建议**：
  1. 默认 `env` 继承策略改为 `safe`：剥离 `*_API_KEY` / `*_TOKEN` / `*_SECRET` / `*_PASSWORD`；拒绝 `PATH`、`LD_PRELOAD`、`NODE_OPTIONS`、`BASH_ENV`、`ENV`、`SHELLOPTS`、`PYTHONPATH` 等危险键；提供 `PI_ASYNC_ENV_INHERIT=all` 逃生门。
  2. `metadata.outputFile` 读取前校验 `realpath` 在 dataDir 内。
  3. delayed env 只存键名 + 值放 0600 独立文件；`async_status`/面板只显示键名。
  4. 数据目录移到 session 目录或 `~/.pi/async/<sessionId>`，不要默认落在项目根。

#### P0-7 面板 kill 的 Promise 没有 catch

- **事实**：`src/tui/panel.ts:293` 是 `void registry.kill(task.taskId, "user")`，没有 `.catch`；`registry.kill` 在子进程组未能确认退出时会抛 `Descendant processes may have leaked`（`registry.ts:344`）。
- **影响**：Node ≥22 默认 `unhandledRejection` 会走 throw；pi 有 `uncaughtException` 处理器，最终 `process.exit(1)`。一次 kill 失败可能把整个 pi 带走。
- **建议**：`void registry.kill(...).catch((e) => { actionError = String(e); requestRender(); })`；工具层已有 try/catch，面板层补齐。

#### P0-8 两个“已实现”的 API 其实是 no-op

- **事实**：
  - `src/core/bus.ts:12-35` 的 `ui.setActivity` 在 pi 1.2/1.4/1.5 的 `ExtensionUIContext` 中都不存在；三处上报全部静默返回。
  - `src/tui/panel.ts:316` 的 `host.ui.copyToClipboard` 也不存在；`c` 键永远走 `notify` fallback。
- **影响**：文档/契约里的 activity/OSC busy 承诺不成立；用户按 `c` 只会看到一条 toast，不是复制。
- **建议**：
  - 保留 feature-detect shim（未来上游若加 `setActivity` 可自动生效），但**不要把它写进能力列表**；当前用 `ui.setStatus` 做 footer 汇总，或在 README 明确“activity API 依赖上游，官方 pi 暂无”。
  - `c` 键改成“显示 output 路径”或删除；不要保留一个永远走 fallback 的“复制”语义。

### P1：工具契约、watch、TUI、性能

#### P1-1 工具面“静默成功”/“只认 id”

| 问题 | 事实 | 建议 |
|---|---|---|
| `async_kill` 未知 id 静默成功 | `registry.kill` 找不到 task 直接 return（`registry.ts:317`）；工具返回 `alreadyTerminal:false`、无 status | 未知 id → `isError:true`，错误文案列出候选 |
| `async_wait/logs/kill` 只认 taskId | 实测模型传 `name` 报 `Unknown task id(s)` | 接受 `name` 别名；重名时报错并列出候选 id |
| 非 sync 传 `onTimeout` 静默忽略 | `tools/index.ts:69-78` 只有 sync 分支读 | 与其他模式参数一致：非 sync 传即 throw |
| sync 非 0 退出不置 `isError` | `toolResult(r)` 默认 `isError=false` | 至少 `status:"failed"` 时置 `isError:true`，或在结果里加显式 `ok:false` |
| `async_status` 默认只列活跃 | `tools/index.ts:96,104`；历史是“最近创建的 50 个” | 默认仍活跃，但加 `status` / `name` / `limit` 过滤；`includeHistory` 按完成时间排序 |

#### P1-2 watch 语义与边界

| 问题 | 事实 | 建议 |
|---|---|---|
| 组内条件是 OR，不是 AND | `watch.ts:217-229` 首个 matched 即返回 | 文档写清；增加 `match:"all"|"any"`（默认 any，保持兼容） |

#### P1-4 性能与存储

| 问题 | 事实 | 建议 |
|---|---|---|
| watch 每 tick 整文件读 | `registry.ts:238-248` 读 `.output` + `.stdout` + `.stderr` 全量 | 只读尾部窗口（与 watch 64K 窗口对齐） |
| `logs()` 整文件读再截断 | `registry.ts:303-313` | 用 `open/read` 尾部；与面板 `readUiOutput` 复用 |
| 面板列表每帧读 running 输出 | `panel.ts` 列表行取最新输出 | 用 tail 读；缓存最近一行 |
| 无全局磁盘配额 | 32 × 3 × 20MiB ≈ 1.9GiB/dataDir | 增加 `PI_ASYNC_TOTAL_BYTES` 或按 dataDir 统计 |
| 每个 pid 一个 dataDir，旧目录永不清理 | `extensions/index.ts:27-34`；prune 只管当前 dataDir | 用 sessionId 目录 + 启动时清理 N 天前目录 |
| 非终态任务不 prune | `registry.ts:449-451`；实测 2 条孤儿 running 永久残留 | 启动时把“pid 已死且超过 N 小时”的非终态标 lost/删 |

| 写流背压未处理 | `spawn.ts:38-41` 忽略 `write()` 返回值 | 监听 drain 或限制 chunk 缓冲 |

#### P1-5 通知体验

- 没有 `registerMessageRenderer`，用户和模型看到裸 XML；legion 的 `subagent-notify` 已有卡片渲染，pi-async 可以对齐。
- 通知不合并（REV-9 明确不做），多任务同时完成会各发一条、各可能 `triggerTurn`；建议至少加一个 50–100ms 的批量窗口，合并成一条“N tasks completed”消息。
- `summary` 只给 8KiB tail，失败时 `guidance` 只指向 `async_logs`；可以在通知里直接给最后一条错误行 + 退出码。
- `notified` / `outputConsumed` 不出现在 `async_status` 的显式字段说明里（虽然 snapshot 有），模型难以判断“我是否已经收过”。

#### P1-6 factory 生命周期偏差

- pi 文档明确：不要在 factory 启动 process/socket/watcher/timer；应延后到 `session_start` 或真正需要资源的 command/tool/event。
- 当前 `init()`（factory）里 `reloadFromDisk()` 会为 pending delayed 建 `setTimeout`、为 running 建 100ms watcher；`SettleGuard.register()` 会建 60s heartbeat。
- **不建议现在做全量 registry per-session 迁移**（会改 5 工具 + TUI + guard + 182 测试）。建议小步：
  1. heartbeat 移到最后一次 `session_start` ctx；
  2. `dataDir` 改 lazy resolver（首次 tool/session_start 时解析）；
  3. `reloadFromDisk` 延后到 `session_start`；
  4. 保留 factory 只做工具注册。
- 如果未来需要“reload 后完整恢复超时/退出码/waiter”，再上 per-session holder。

### P2：文档、仓库卫生、发布工程

- **契约漂移**：`CONTRACT.md` 写“四种任务模式”但代码只有三种；README 键位表 `k` 两种语义；README 配置表缺 `PI_ASYNC_RAIL_LINGER_MS`；`async_status` 默认历史语义未写。
- **仓库卫生**：根目录 65MB `core`（已忽略）；12 个残留 worktree 约 425MB；`.ruff_cache` 无根级 ignore；`package-lock.json` 版本仍 0.1.0。
- **CI**：只测 node22 + 仓库内 pi 1.2.0 类型；docker 固定 pi 1.2.0；没有 publish workflow / tag 自动化。
- **死代码**：`pi.off` 兜底（官方无 `off`）、`setActivity`/`copyToClipboard` 分支、rail 键盘滚动、`fitRailRow` 未直测。
- **未用 1.5 能力**：`promptSnippet`、`onUpdate`、`truncateHead/Tail`、`keyHint`、`setStatus`、`registerMessageRenderer`、`pi.events`。

## 4. 建议路线图

### 4.1 版本策略：建议 0.3.0 单批发布

**推荐 0.3.0，而不是 0.2.1 维护分支。** 理由：

1. HEAD 已有 6 个未发版提交，包含 crash fix；0.2.1 若只 cherry-pick 崩溃修复，用户拿到的是“崩溃修了但 cwd/通知仍错”的版本，很快要再升一次。
2. `CHANGELOG Unreleased` 已经有 5 条 breaking（footer 下架、删快捷键、rail ≤4 行、面板百分比），0.2.1 要么撒谎要么把这些提交摘掉。
3. 如果把 `peerDependencies` 抬到 `^1.5.0`（为了 `ctx.cwd`/`onUpdate` 等），本身就是 semver breaking，和 0.3.0 天然同一批。
4. pi-async 是 0.x + 小用户群，一次干净升级比两次小版本更省支持成本。

**例外**：如果 0.3.0 需要两周以上，先发 0.2.1（只带 stale-ctx 修复 + 版本/锁文件修正），把崩溃风险先降下来。

### 4.2 0.3.0 的“最小可信包”（5 个工作流 + 1 个交付门）

| 顺序 | 工作流 | 具体改动 | 验收 |
|---|---|---|---|
| 1 | **cwd 正确性** | `execute` 接 `ctx.cwd`；`spawnDetached` 传 `cwd`；delayed 持久化 cwd；TUI rerun 用 session cwd | 新测试：进程 cwd=/root，session cwd=/tmp/x，`async_run("pwd")` 输出 `/tmp/x` |
| 2 | **通知诚实化** | 删假重试；claim 后置；`session_start` 补发；`async_status` 暴露 notified/outputConsumed | ① 发送失败 `notified=false`；② 成功后 true；③ reload 后补发一次；④ 状态可查 |
| 3 | **工具契约不撒谎** | `async_kill` 未知 id 报错；`name` 别名；非 sync 传 `onTimeout` 报错；sync 失败 `isError`；`async_status` 过滤/排序 | 4 条回归测试，错误文案含下一步 |

| 6 | **交付门** | peerDeps/CI 换 pi 1.5.0；publish workflow；lock 版本；CHANGELOG 定稿；tag v0.3.0 | `npm pack --dry-run` 正确；CI 全绿；`npm view pi-async version` = 0.3.0 |

### 4.3 0.3.1 / 0.4 再做

- **TUI 体验**：详情滚动、固定 header/footer、单例 overlay、Kitty 键位、regular 模式入口。
- **通知卡片**：`registerMessageRenderer`；批量合并；失败通知带最后错误行。
- **性能**：watch/logs/panel 全部改尾部读；finalize 合并写盘；写流背压。
- **存储 GC**：全局配额、跨 dataDir 清理、孤儿 running 自动 lost。
- **watch v2**：`match:"all"|"any"`、`killOnSuccess`、正则执行超时/worker。
- **工具进度**：`onUpdate` 报 elapsed + 最后一行；`promptSnippet`/`promptGuidelines`。
- **reload 完整恢复**：`timeoutAt`、`watchDeadline`、退出码、waiter（如果要跨 reload 等待，需要重新设计 waiter 生命周期）。
- **跨进程/多会话**：如果确实需要，再考虑 daemon/IPC；当前同进程模型足够。

### 4.4 不建议现在做

- **不要把 registry 生命周期整体迁到 `session_start`**：收益 80% 可由“cwd 线程化 + lazy dataDir + heartbeat 后移”拿到；全量迁移会改 5 工具 + TUI + guard + 182 测试，且当前没有第二个 stale-ctx 崩溃信号。
- **不要加第 6 个工具**：5 工具面是冻结契约；列表/过滤扩展 `async_status` 即可。
- **不要追 `setActivity`**：官方 pi 1.2–1.5 都没有；保留 feature-detect 即可，别把它写进能力承诺。
- **不要现在做 TUI 大改**：面板是可选观测面；先把工具面/通知/cwd 的“说谎”修掉。
- **不要做 agent 编排**：subagent/legion 已经覆盖；pi-async 只做 shell 任务运行时。
- **不要无条件启用 settle guard**：`continue:true` 可能死循环；legion-only + aborted 兜底是更稳的边界。

## 5. 验收与测试建议

### 5.1 新增回归测试

1. **cwd**：session cwd 与进程 cwd 不同，`async_run("pwd")` 输出 session cwd。
2. **notify**：`sendMessage` 抛错 → `notified=false`；成功 → `true`；`session_start` 补发未确认任务；`async_wait` 消费后不补发。
3. **settle**：`custom_message` draft 进入 `event.entries`；`agent_settled({aborted:true})` 发 followUp；达到 maxReminders 后放行。
4. **kill**：未知 id → `isError`；D4 completed+alive → 返回 `processAlive`/`killKind`；kill 确认失败 → 面板不崩。
5. **env**：默认不继承 `*_API_KEY`；`PATH` 覆盖被拒；`PI_ASYNC_ENV_INHERIT=all` 才全量继承。
6. **path**：`metadata.outputFile` 指向 dataDir 外 → `async_logs` 报错。
7. **reload**：`session_shutdown({reason:"reload"})` 不 kill running；`quit` kill；`taskTimeoutMs` 重建。
8. **watch**：`match:"all"` 的 AND 语义；`json_path_exists` 的盲检策略；64K 窗口边界。
9. **storage**：孤儿 running 在启动时标 lost/清理；跨 dataDir 旧目录清理。
10. **TUI**：面板打开时 finalize 触发 `requestRender`；详情滚动不裁掉 footer；overlay 单例。

### 5.2 CI 矩阵

- Node 22 + 24（当前 engines `>=22.19.0`）。
- pi `1.5.0` 作为主类型基线；保留 `1.4.0` 兼容 job（如果还要支持）。
- `npm pack --dry-run` + 安装到临时目录 + `pi --version`/扩展加载 smoke。
- 1.5.0 `pi-schema` 对 5 工具 schema 的实际校验/报错测试。
- 发布 workflow：tag `v*` → `npm publish` + GitHub Release。

## 6. 产品定位建议

**守住：**

- 后台 shell 任务运行时：启动、等待、读取、杀死、超时、watch。
- 诚实状态面：任务状态、退出码、kill/failure 原因、是否已通知、是否已消费。
- 与 legion 的弱耦合：`PI_LEGION_NODE_ID` + settle 提醒；不要反向依赖 legion 内部实现。

**降级为可选：**

- TUI 面板：保留 rail + `/async` 文本输出即可；鼠标/快捷键/滚动是锦上添花。
- activity/OSC busy：官方 API 不存在，保留 shim 但不承诺。
- `delayed` 模式：使用率 6.5%，且 env 持久化有安全成本；保留但默认不宣传。
- 通知卡片/批量合并：体验增强，不阻塞核心。

**砍掉：**

- `ui.copyToClipboard` 伪能力。
- 无人消费的 heartbeat entry（或改成真正的 liveness 信号）。
- delayed env 明文进 snapshot / TUI metadata。
- “agent 编排”的隐含野心（D1 已定不做）。
